# GLM-5.3 (W4A4C8 MXFP4)

`glm_moe_dsa` (`GlmMoeDsaForCausalLM`) is a **256-expert MoE** with MLA attention and
DeepSeek-style sparse attention (DSA), served here with a **1,048,576-token context**. GLM-5.3
shares its base model with [GLM-5.2](./glm-5.2-w4a8c8.mdx) but has different post-training,
and it **always reasons before answering**: it has no non-thinking mode, only a reasoning
effort of `max` (the default), `high` or `low`. It was validated on **one Atlas 850 node =
8 × Ascend 950DT 96 GB** as a **single aggregated engine** (TP8 with decode context parallel
8), through the product MaaS gateway.

Load is a **replay of real coding-agent sessions** (Exgentic v2, `claude_code` working
SWE-bench tasks) swept over concurrent sessions, run twice: once with the default reasoning
effort (`max`) and once with every request asking for `low`. Nothing else ran on the service.

:::tip
**In short — this deployment served 16 concurrent coding-agent sessions with time to first
token (TTFT) P90 under 10 s at both reasoning efforts; 32 did not.**

At 16 sessions TTFT P90 was **2.12 s** (`max`) and **2.65 s** (`low`). At 32 sessions requests
queued behind the engine's limit of 18 running requests (`max-num-seqs`) and TTFT P90 rose to
25.4 s and 17.7 s, while KV usage peaked at 14 %: the limit is that 18-request gate, set for
150k-token requests, not memory. A higher gate is not measured on this page, and nothing
between 16 and 32 sessions was measured.

**`low` shortens reasoning but does not add sessions.** At 16 sessions the first answer token
(after reasoning) P90 fell from 31.4 s to 14.1 s and the end-to-end P90 from 40.2 s to 32.1 s
(P50 unchanged at about 7 s); 30–40 % of requests still reasoned first. In exchange TTFT was
about 25 % longer and the gap between streamed tokens 15–30 % longer, and the effect on answer
quality was not evaluated. `low` applies only to requests that send
`chat_template_kwargs: {"reasoning_effort": "low"}`; the service default stays `max` (a
server-side default was not tested).
:::

## Model configuration \{#model-configuration}

| Parameter | Value |
|---|---|
| Parallelism | TP8 + expert parallel (experts over the 8 cards), DCP8 (decode context parallel: a sequence's main KV cache is split across the 8 cards, 128 tokens at a time), one engine on the whole node |
| `max-model-len` | 1,048,576 |
| `max-num-batched-tokens` | 16,384 |
| `max-num-seqs` (admission gate) | 18 (see below) |
| `gpu-memory-utilization` | 0.9 |
| KV cache | FP8 main KV and FP8 indexer cache; 3,023,872 tokens (engine-reported, 26.43 GiB per card), 2.88 full 1M-token requests |
| Speculative decoding | `deepseek_mtp`: the model's multi-token-prediction (MTP) layer drafts 5 tokens per step (drafter eager) |
| Graph mode | `FULL_DECODE_ONLY`; `--async-scheduling`; prefix caching on |
| `additional-config` | `enable_cpu_binding` |
| Tool calls / reasoning | `--enable-auto-tool-choice --tool-call-parser glm47 --reasoning-parser glm47`; reasoning is returned in its own field, apart from the answer |
| Notable env | `VLLM_USE_FASTOKENS=1` (fastokens tokenizer: an 800k-token prompt in 0.05 s instead of 2.2–2.7 s), `HCCL_OP_EXPANSION_MODE=AIV`, `HCCL_BUFFSIZE=900` |

:::note
**Why `max-num-seqs` is 18.** The engine admits a request when its next chunk fits; it does not
reserve the request's whole KV. Above what KV can hold, long requests are admitted, then
preempted and recomputed when KV fills: at 20, with 150k-token inputs, KV reached 100 % and
one preempted request stalled for 311 s. A 150k-input + 10k-output request with no shared
prefix needs 157 of the 2,953 KV blocks, so 18 fit. With shorter requests or shared prefixes
KV holds more, but the gate stays at 18 — on the coding replay below it is what limits the
session count, not KV.
:::

**Reasoning effort per request.** The service does not change the default, so a request
without the parameter reasons at `max`. To ask for less, send it in
`chat_template_kwargs`:

```json
{"model": "GLM-5.3-w4a4c8-mxfp4", "messages": [...],
 "chat_template_kwargs": {"reasoning_effort": "low"}}
```

With vLLM 0.30.0 a top-level `"reasoning_effort": "low"` is ignored (the rendered prompt still
says `Reasoning Effort: Max`), and `"enable_thinking": false`, which GLM-5.2 accepts, has no
effect on GLM-5.3: the rendered prompt is unchanged and the model still reasons.

### Request path

MaaS → KServe ingress gateway → the engine. With a single replica there is no endpoint
picker. The gateway route that MaaS forwards to comes from `spec.router.route` and
`spec.router.gateway` in the manifest (the console form's "expose externally" option); the
model name clients send is `spec.model.name`.

## Deploy

**Before you deploy, check the node's HCCL topology.** HCCL (Huawei's collective communication
library, which the 8 cards use to exchange data) reads `/etc/hccl_rootinfo.json`, which the
Ascend device plugin mounts into the pod from the node. It must list only network levels that
pass traffic. On the validated Atlas 850 node the second network level (through a UB switch,
for multi-node setups) does not pass traffic between the cards, but the generated file listed
it. Once a collective grew past 32–128 MB per rank, HCCL picked an algorithm that uses that
level and all 8 cards waited until `HCCL_CONNECT_TIMEOUT` (a 1M-token request hung this way).
Regenerating the file with the first level only (`mindcluster-tools rootinfo --max_level 1`)
fixed it; the engine reads it at start-up.

| Spec | File |
|---|---|
| passwd `ConfigMap` for uid 1000 + `LLMInferenceService` | [`glm-5.3-w4a4c8-mxfp4-agg-llmisvc.yaml`](https://github.com/alauda/aml-docs/tree/master/docs/en/plan/validated_models/ascend/assets/glm-5.3-w4a4c8-mxfp4/glm-5.3-w4a4c8-mxfp4-agg-llmisvc.yaml) |

```bash

curl -sO $base/glm-5.3-w4a4c8-mxfp4-agg-llmisvc.yaml

# 1. Edit the file first: replace every `demo` with your namespace, point spec.model.uri

# 2. Wait for the engine: about 7.5 minutes from pod start to ready; loading the weights
#    (~1.5 minutes) and engine initialisation (~2 minutes, including compilation and graph

# 3. Publish on MaaS: on the service, Actions → Enable for MaaS; then add the model under
#    MaaS → Models → Published Models and to a subscription.

  -H "Authorization: Bearer $MAAS_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"GLM-5.3-w4a4c8-mxfp4","messages":[{"role":"user","content":"hello"}],
       "chat_template_kwargs":{"reasoning_effort":"low"}}'
```

The benchmarked service was created in the console form (model from a PVC, runtime
`infernex`, chip type A5, TP 8, the env and args above, hardware profile `ascend-a5-8npu`
with 8 × `huawei.com/npu`), with the fields marked "not in the form" in the manifest added in
the YAML view. Creating it with `kubectl apply` gives the same object.

:::warning
- **Change engine flags by deleting and re-creating the service.** A rolling update cannot
  place a second 8-card pod on the node.
- **The platform's own A5 image (vLLM-Ascend v0.23.0) cannot run GLM-5.3.** The manifest
  replaces the image. Do not use the `v0.30.0rc2-a5` image either: it does not support an FP8
  main KV cache together with DCP on 950DT.
- In the console, the hardware profile's node selector was not carried over to the pod, and
  the custom resource option offers no NPU type: use a hardware profile, and on clusters with

:::

## Benchmark method \{#benchmark-method}

`aiperf 0.12.0`, replaying **real coding-agent sessions** with
`timingMode: agentic_replay`. Load is set by the number of **concurrent sessions**: each
session sends its next request after the gap recorded in the trace (the agent's tool time),
and a finished session is replaced by the next one from the pool. Nothing else ran on the
service during either sweep. The corpus, sampling and pass criterion are the same as on the
[GLM-5.2](./glm-5.2-w4a8c8.mdx) page.

| Item | Setting |
|---|---|
| Corpus | [Exgentic agent-llm-traces-v2](https://huggingface.co/datasets/Exgentic/agent-llm-traces-v2) (revision `4b8ad4ab`), `harness=claude_code`, `benchmark=swebench`: 495 sessions |
| Corpus profile | median 37 calls per session; mean input 27k tokens per call; per-session peak context p50 36k / p90 66k / p99 103k / max 121k; ~97 % of each call's input repeats the previous call (~800 new tokens per turn); mean recorded output 211 tokens (the replay sends the recorded inputs; GLM-5.3 writes its own outputs, reasoning included, so OSL below differs) |
| Replay | each session starts at a random point 25–75 % into its recorded trajectory, so sessions are at mixed depths from the start; sequential sampling, seed 42 |
| Rungs (load levels) | 8 / 16 / 32 / 64 sessions, 900 s of timed requests each (+120 s for in-flight requests to finish), one pass per reasoning effort; warm-up requests are not counted |
| Reasoning effort | sweep 1: requests as recorded (`max`); sweep 2: every request adds `chat_template_kwargs: {"reasoning_effort": "low"}`. Nothing else changed, the engine included |
| Cache isolation | `cacheBust: first_turn_prefix` — a unique marker in each replay's first user message, so a rung cannot reuse an earlier rung's conversation prefixes (the shared system prompt and tool definitions before that message can still be cached), while turns within a session still reuse each other |
| Ingress | product MaaS gateway (API key), streaming, engine-reported token counts |
| Engine counters | the engine's `/metrics`, read every 3 s from the load generator |

**Pass criterion (set before the run).** Every figure in the result tables is measured over
the **second half of each rung** — its timed requests sorted by start time, from the first
start in that half to the last end. A rung passes when, in that window, the TTFT P90 is
**under 10 s** and the window is stable (median inter-token latency of its two halves within
25 %). The result is the highest passing rung, without interpolation.

TTFT is the time to the first streamed token, which for GLM-5.3 is often reasoning;
**first answer token** is the first non-reasoning token. **End-to-end** is the time from
sending a request to its last token. **ITL** (inter-token latency) is the gap between streamed
tokens. ISL / OSL are each request's input / output tokens (OSL includes reasoning).
**Output TPS** and **total TPS** (input + output) count the tokens of the window's requests
over the window length, the definition used on the [overview](../index.mdx) page; they miss
output from requests that started before the window, which matters here because responses
are long. **Engine output** is the engine's own count of output tokens per second over the
window. **Requests completed/s** counts requests that ended inside the window.
**Achieved sessions** is the time-averaged number of sessions with a request in flight; it is
below the nominal count because a replayed session waits out its recorded tool time between
turns. **Per-session output** is 1,000 / average ITL, the rate one user sees while a response
streams.

New input computed is what prefill had to compute after the prefix-cache hit (93.5–93.7 %).

- **Reasoning gets shorter, not rarer.** 30–40 % of requests still reason before answering
  (7–9 points fewer at 16 and 32 sessions, about the same at 8 and 64), but each reasoning
  block is much shorter, and responses are 30–57 % shorter overall.
- **The first answer token comes 1.7–3.6× sooner, but still not within 10 s** at any rung. The
  sweep passes on TTFT, as GLM-5.2 did; if your client waits for answer text, judge by the
  first answer token instead.
- **Sessions move faster.** With shorter responses each session reaches its next turn sooner,
  so the same number of sessions completes 30–112 % more requests per second and computes
  more new input. The engine produces fewer output tokens per second, and per-request ITL
  is 15–30 % longer (the extra prefill work shares steps with decoding — inferred, not
  profiled). TTFT P90 at 8 and 16 sessions is about 25 % longer, still far under 10 s.
- **The two sweeps' windows hold different requests**: with `low`, sessions get further into
  their trajectories in the same 900 s. Pairing the same session and turn across the two
  sweeps (all timed requests) gives the same direction with a smaller step: first answer token
  P90 46.5 → 12.7 s at 8 sessions and 39.3 → 18.0 s at 16.

## Caveats \{#caveats}

- **These sessions are shorter than 128k-token agent sessions.** Inputs reached 86k tokens in
  the measured windows (P99 48k–84k). Longer sessions make prefill and decode heavier and fill
  KV sooner; do not carry the 16-session figure over to 128k-token sessions.
- **Each rung was measured once.** How long the model reasons varies from run to run; the
  first-answer-token and end-to-end percentiles can move by about 30 % between repeats of the
  same configuration. At 8 sessions only 10–12 distinct sessions (finished ones are replaced)
  fall in the window, so a few long reasoners dominate its percentiles (which is why its `max` first answer token P90 is above
  the 16-session one).
- **The effect of `low` on answer quality was not evaluated.** This page measures speed only.
  A short check outside the sweep (the same small coding prompt, twice each) produced 790–804
  output tokens at `max`, mostly reasoning, and 306–316 at `low` with no reasoning.
- **Accuracy was not evaluated here.** The [vLLM-Ascend v0.30.0 guide](https://docs.vllm.ai/projects/ascend/en/v0.30.0/tutorials/models/GLM5.2.html)
  records GSM8K 96.97 % for a local GLM-5.3 W4A4C8/MXFP4 checkpoint on one 950DT node (not
  matched to a published revision), and states that the record verifies start-up and short
  requests, not long inputs, tool use or performance. Evaluate accuracy for your own workload before production use.
- **1M-token requests are slow without a cached prefix.** A single request of about 1M tokens
  sent through MaaS took 423 s to the first token and 445 s in total (measured once, before
  fastokens was enabled). Two concurrent 1M requests were not tested.
- **Errors seen:** besides the 5 failures above, most warm-up requests (one per session slot,
  sent by aiperf at the start of each rung) ended with reasoning but no answer within the
  warm-up token limit; warm-ups are not counted.
