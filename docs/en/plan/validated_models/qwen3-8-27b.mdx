# Qwen3.8-27B (NVFP4, NVIDIA)

`qwen3_5`-architecture dense model — a Gated DeltaNet linear-attention hybrid (48 of 64
layers are linear attention) with a native MTP head, 27B parameters, served as
**RedHat NVFP4** (~25 GB) with **DFlash2 speculative decoding**. Validated on a single
**NVIDIA RTX PRO 6000 Blackwell** with community **vLLM v0.31.0**, deployed as a plain
KServe `LLMInferenceService` behind the Alauda AI **MaaS gateway**. The GPU memory budget
was capped at **84 GB** to emulate an RTX PRO 6000D. Context length **128k**.

## Model identity

| Field | Value |
|---|---|
| Publisher | Qwen (Alibaba); NVFP4 quantization by Red Hat AI |
| Architecture | `qwen3_5` — Gated DeltaNet linear attention (48 layers) + full attention (16 layers) + native MTP; multimodal-capable, served text-only (`--language-model-only`) |
| Checkpoint | [`RedHatAI/Qwen3.8-27B-NVFP4`](https://huggingface.co/RedHatAI/Qwen3.8-27B-NVFP4) @ `2889ddee` (24.69 GB): MLP in NVFP4 (W4A4); attention, GDN projections and layers 56–63 in FP8 |
| Draft model | [`incoai/Qwen3.8-27B-DFlash2`](https://huggingface.co/incoai/Qwen3.8-27B-DFlash2) @ `015e7956` (3.85 GB), 7 tokens per draft |
| License | Apache 2.0 (base model, NVFP4 checkpoint and draft model) |
| Published accuracy retention | ~99% of the original (e.g. SWE-Bench 78.0 vs 78.8, per the checkpoint card) |

## Validated hardware × stack

| Platform | Engine | Version / config | Status |
|---|---|---|---|
| NVIDIA RTX PRO 6000 Blackwell 96 GB × 1 (SM120), capped to 84 GB; AWS g7e.2xlarge | vLLM (community) | `docker.io/vllm/vllm-openai:v0.31.0` (CUDA 13.0.2), NVIDIA driver 580.126.09 | ✅ function checks, single-stream / long-input / full-128k, Exgentic agent replay capacity, through MaaS |

:::note
The speed numbers were measured on the standard **96 GB** RTX PRO 6000 with the memory
budget scaled down to **84 GB** (`--gpu-memory-utilization=0.805`). This reproduces the
KV capacity of an RTX PRO 6000D, **not its compute or bandwidth**, which are lower —
re-measure on a real 6000D before quoting 6000D speeds. Alauda AI's bundled vLLM (0.23.0)
was not used: the community v0.31.0 image is brought in by an `LLMInferenceServiceConfig`
that overrides only the container image.
:::

## Model configuration

| Parameter | Value |
|---|---|
| `max-model-len` | 131072 |
| `gpu-memory-utilization` | 0.805 (84 GB budget on a 96 GB card; use 0.92 on an RTX PRO 6000D) |
| `max-num-seqs` | 32 |
| `max-num-batched-tokens` | 8192 (prefix caching on; hybrid block size 784 → 7,840 tokens per step) |
| KV cache dtype | BF16 (Qwen3.5-family checkpoints do not load KV scales, vLLM #54623) |
| Speculative decoding | DFlash2, `num_speculative_tokens=7` |
| KV capacity | 515k tokens with DFlash2 (812k without speculative decoding) |
| Tool calls / reasoning | `--enable-auto-tool-choice --tool-call-parser qwen3_coder --reasoning-parser qwen3` |
| HTTP keep-alive | `VLLM_HTTP_TIMEOUT_KEEP_ALIVE=3700` (longer than the gateway's idle reuse; avoids 503 `UC`) |

## Deploy

| Step | File |
|---|---|
| 1. Download the checkpoint and the draft model (PVCs + Job, sha256-verified) | [`qwen3-8-27b-download.yaml`](https://github.com/alauda/aml-docs/tree/master/docs/en/plan/validated_models/assets/qwen3-8-27b/qwen3-8-27b-download.yaml) |
| 2. Engine image config + `LLMInferenceService` | [`qwen3-8-27b-llmisvc.yaml`](https://github.com/alauda/aml-docs/tree/master/docs/en/plan/validated_models/assets/qwen3-8-27b/qwen3-8-27b-llmisvc.yaml) |

```bash
base=https://raw.githubusercontent.com/alauda/aml-docs/master/docs/en/plan/validated_models/assets/qwen3-8-27b
# edit the namespace first; label the GPU node the PVCs should land on:
kubectl label node <gpu-node> validated-model=qwen3-8-27b
kubectl apply -f $base/qwen3-8-27b-download.yaml
kubectl -n <your-namespace> wait --for=condition=complete job/qwen38-27b-download --timeout=2h
kubectl apply -f $base/qwen3-8-27b-llmisvc.yaml
kubectl -n <your-namespace> get llminferenceservice qwen38-27b -w

curl -s https://<maas-host>/v1/chat/completions \
  -H "Authorization: Bearer $MAAS_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.8-27b","messages":[{"role":"user","content":"hello"}]}'
```

The first start takes about 9.5 minutes (weights ~3 min from the local disk, then kernel
compilation, CUDA-graph capture and FlashInfer tuning); the compile cache on
`qwen38-27b-cache` makes later starts skip compilation.

:::warning
- With speculative decoding on, vLLM rejects `min_p` and `logit_bias` (HTTP 400).
- The answer text starts with `"\n\n"` after the reasoning parser splits the thinking off;
  strip leading whitespace in the client.
- `nvidia-smi` reached **82,013 MiB** under full KV load — about 3.1 GiB above the 84 GB
  plan (vLLM does not budget some GDN scratch buffers, #54775). An RTX PRO 6000D still has
  ~3.5 GiB left; to stay strictly inside 84 GB, lower `--gpu-memory-utilization` to 0.785.
:::

## Benchmark results

`aiperf 0.12.0` (NVIDIA image), all through the MaaS gateway. Token counts use the
engine-reported usage.

**Single stream and long input**

| Workload | TTFT p50 | ITL p50 | Per-request output p50 | Tokens per step |
|---|--:|--:|--:|--:|
| Random prompt, 1k in / 1k out, 20 requests | 110 ms | 8.2 ms | 122.6 tok/s (55.1 without speculative decoding) | — |
| Agent replay, 1 session, 15 min (Exgentic `claude_code` × `browsecompplus`) | 0.65 s | 12.1 ms | 82.5 tok/s (51.8 without) | 4.3 |
| Agent replay, 4 sessions, 15 min | 0.74 s | 15.8 ms | 63.3 tok/s (40.5 without) | 4.0 |
| 127k input, 256 out, 20 requests | 19.8 s | 35.2 ms | 28.4 tok/s (42.1 without) | 2.9 |

Near 128k input the cost of verifying 8 tokens per step outweighs the accepted drafts,
so DFlash2 is ~31% slower there than no speculation. **Full-128k requests (~126k in /
1k out): 3 run at once with DFlash2** (vLLM's own estimate 3.93; KV peak 71%, 0
preemptions); without speculative decoding the same budget holds 6.

**Concurrent requests under an agent workload**

This answers "how many requests can one card process at the same time" for an agent
workload shaped like the target production agent's real usage. That agent makes 3–4
model calls per question; per-call input is median ~11.5k / p90 ~21k tokens on tool turns
and ~15k / ~30k on the final turn, and output is ~100–300 tokens on tool turns and median
~1.1k (including thinking) on the final turn. The replayed workload is a real agent corpus
with similar inputs: Exgentic v2 `openai_solo` × `swebench`, per-call input median
~11–16k / p90 ~20–38k tokens as received by the engine, output median 42–96 tokens. It was
replayed with `timingMode: agentic_replay` (recorded call gaps, lanes starting at 25–75% of
each trajectory, per-session cache-bust), 15 minutes per tier. Because the number of
requests actually in flight varies a lot between sessions, every request is grouped by
the time-averaged number of requests in flight during its lifetime (first 120 s of each
tier excluded). Six tiers, 0 errors: sessions recorded with `DeepSeek-V3.2` at 8 and 16
concurrent sessions (realistic ~0.9 s gaps between calls) plus sessions recorded with
`claude-opus-4-5` at 4 / 8 / 12 / 16 (closest input lengths, low in-flight load).

| Requests in flight | Requests | TTFT p50 / p90 | First answer token (after thinking) p50 / p90 | ITL p50 / p90 | Per-request output p50 (slowest 10%) | Input p50 | Output p50 / p90 |
|--:|--:|--:|--:|--:|--:|--:|--:|
| 1–2 | 1,367 | 0.24 / 0.37 s | 0.62 / 1.60 s | 11.1 / 18.2 ms | 89.8 (54.9) tok/s | 11,205 | 42 / 263 |
| 3–4 | 580 | 0.30 / 0.52 s | 0.81 / 2.09 s | 14.1 / 22.5 ms | 71.0 (44.4) tok/s | 11,773 | 42 / 233 |
| 5–6 | 557 | 0.40 / 0.64 s | 1.25 / 3.11 s | 19.0 / 27.8 ms | 52.6 (36.0) tok/s | 14,765 | 88 / 288 |
| **7–8** | 891 | **0.44 / 0.68 s** | 1.36 / 3.90 s | 20.2 / 28.9 ms | **49.5 (34.6) tok/s** | 16,494 | 96 / 377 |
| 9–12 | — | not measured | | | | | |
| 13–16 | 638 | 3.34 / 8.21 s | 7.70 / 18.0 s | 92.0 / 160 ms | 10.9 (6.3) tok/s | 14,346 | 92 / 347 |

**Up to 8 requests at the same time the service stays responsive** (TTFT p90 ≤ 0.7 s,
~50 tok/s per request). At 13–16 the KV cache fills (96%), prefix-cache hits drop from
~90% to 28% because cached history is evicted between turns, and every request slows to
~11 tok/s. DFlash2 acceptance stayed at 33–38% (3.3–3.7 tokens per step) across tiers.

:::note
**How to read these.** Quote this result as concurrent **requests**, not users or
sessions: a replayed session spends part of its time waiting on recorded tool calls, so
the same session count produces very different in-flight load. The corpus outputs are
short (median 42–96 tokens) compared with a final agent answer that includes thinking
(often 1k+ tokens), so the decode side is lighter than such traffic. Two corpus details
shaped the selection: `tool_calling_with_shortlisting` × `appworld` replays the full
468-tool catalogue on every call (inputs ~3× the recording), and sessions recorded with
`claude-opus-4-5`, `gemini-3-pro-preview` and `gpt-5.2` store zero call durations, so the
recorded gaps include the source model's own latency and replay leaves those sessions
mostly idle. With ~30k-token inputs (the `appworld` subset) the picture is the same: ≤ 8
in flight comfortable, KV full and preemptions from ~17.
:::
