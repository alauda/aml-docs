# Qwen3.5-397B-A17B (W8A8)

`qwen3_5_moe`-architecture model (`Qwen3_5MoeForConditionalGeneration`) — a **512-expert
MoE** (10 experts per token + 1 shared expert) with a **hybrid attention stack**: of its
60 layers only **15 carry a full-attention KV cache**, the other 45 are linear-attention
(one full-attention layer every 4). It ships a native **MTP** head and is served as
**W8A8** (~392 GB weights: 373 GB experts + 18 GB non-expert). **397B total /
~17B activated per token.**

It was validated on **Ascend 910B3 (64 GB/card)** in **two topologies on the same 16
cards** — one 16-card cross-node aggregation and one 8-card single-node aggregation —
so that per-scenario placement can be chosen on measured data rather than assumed. Load
is a **replay of real agent traces** (Exgentic v2, `claude_code` harness), swept over
concurrent agent **sessions**, not synthetic fixed-length prompts.

:::tip
**In short — split the 16 cards into two independent 8-card services for chat and coding,
and keep one 16-card service only for RAG.**

On identical hardware and at the same total number of concurrent sessions, two 8-card
islands served chat and coding at **1.7–2.1× lower inter-token latency** and **up to 89 %
higher throughput** than a single 16-card cross-node service — but only while each
island's KV cache has headroom. **RAG must stay on the 16-card service** (30 % of its
requests exceed the window an 8-card deployment can hold), and **coding should move back
to it above ~16 total sessions**, where an island reaches 86 % KV and latency quadruples.
Also: do not hand-write `cudagraph_capture_sizes` — see the caution below.
:::

:::caution
**Do not hand-write `cudagraph_capture_sizes`.** Left alone, this engine sizes the capture
list to cover exactly the largest decode step the admission gate can produce —
`max_num_seqs × (1 + num_speculative_tokens)` tokens. Measured on both topologies here:
gate 64 → captures `[8, 16, …, 128]`; gate 16 → `[8, 16, 24, 32]`. **The default has no
cliff by construction.** A hand-written list silently overrides it, and **any decode step
whose token count exceeds the largest captured size falls back to eager dispatch for the
whole step**.

The unit is **tokens per step, not requests**: with MTP (`k = 1`) each running sequence
contributes 2 tokens per step, so a captured maximum of 64 covers only 32 sequences per
rank. An earlier configuration of this model pinned `[1,2,4,8,16,32,64]` against a gate of
64 — half the coverage it needed. A controlled probe on that deployment measured
**506–675 ms per step above the boundary versus 145 ms below it**, and one rank crossing
it stalls the whole DP group.

Removing the list costs ~9 min of extra graph capture at startup on the 16-card topology
(749 s vs 322 s) and **nothing** in KV cache — the 8-card engine reported the same
375,260-token cache either way.
:::

## Benchmark method \{#benchmark-method}

Closed-loop `aiperf 0.12.0`, replaying **real agent sessions** from the Exgentic v2
corpus (`harness=claude_code`) rather than synthetic prompts. The x-axis is **concurrent
agent sessions**: one session has at most one request in flight, and finished sessions
are immediately replaced, so a rung holds its session count for the whole run.

| Scenario | Corpus subset | Sessions in pool | What it models | ISL (measured avg) |
|---|---|--:|---|--:|
| **chat** | `tau2_retail` | 356 | Customer-support agent, multi-turn tool use | ~22k tokens |
| **coding** | `swebench` | 495 | Coding agent working a repository task | ~30k tokens |
| **RAG** | `browsecompplus` | 451 | Retrieval-heavy browsing agent, long context | ~52k tokens (p90 101k) |

Each rung sends a fixed request count scaled with concurrency
(`max(200, 25 × concurrency)`) so every rung drives each session to the same depth — a
fixed per-rung request count would let high-concurrency rungs spread the same work over
more, shallower sessions and flatter the numbers.

:::note
**Every figure below is measured over the second half of its rung — the steady state.**

Closed-loop replay starts all N sessions at turn 0 at once, so a rung opens with every
session doing a full cold prefill simultaneously; those prefill steps crowd out decode and
inflate ITL until the prefix cache catches up. On this model that alone accounts for a
38–50 % fall in ITL from the first to the last fifth of a rung, on an already-warm engine.
Production traffic is a mixture of session depths, not a synchronized cold start, so the
settled half is the representative operating point and the whole-rung average is
pessimistic. That window is itself re-checked for drift (≤ 25 % change in median ITL
across it); rungs that still drift are marked ⚠️ and excluded from the conclusions.

Engine warm-up is a separate, one-time effect — a fresh process is several times slower
for its first ~600 long-context requests while it compiles shapes — and is absorbed by a
corpus warm-up phase before the sweep.
:::

### Verdict

| Scenario | Recommended topology | Measured basis | Ceiling |
|---|---|---|---|
| **chat** | **Two 8-card islands** | 1.69–2.03× lower ITL and 58–89 % higher throughput than the 16-card service at 8, 16 and 32 total sessions | ~32 total sessions — at 16 per island the gate binds (throughput flat, KV 60 %) |
| **coding** | **Two 8-card islands up to ~16 total sessions; one 16-card service above that** | 2.05× lower ITL at 8 total sessions | An island runs out of KV at 16 coding sessions: 86 % KV, ITL 288 ms, TTFT 10.9 s, throughput *halved* vs. the 16-card service |
| **RAG** | **One 16-card service** (the 8-card cannot run it) | 30 % of RAG requests exceed the 8-card 65536-token window; the 16-card window fits 100 % | 8 sessions measured clean at 78 ms; 16 measured 185 ms but did not clear the stationarity bar |

**Why the split wins where it wins.** Both options use the same silicon, so the gain is
not extra compute — it is that a cross-node DP2 service couples its two ranks. Every
prefill step runs eagerly and blocks decode on *both* ranks, so one island's prefill
bursts cannot disturb the other once they are separate services. Splitting also halves
the blast radius of a node failure and lets each island be tuned for its own scenario.

**Why it stops winning.** An island has one eighth of the cluster's KV cache
(375,260 tokens vs 1,416,463) and admits at most `max-num-seqs` = 16 sequences. Chat
sessions (~23k tokens) fit 16-deep at 60 % KV; coding sessions grow past 28k and reach
86 % KV, at which point latency roughly quadruples over the rung and throughput halves.
RAG sessions (~52k, p90 101k) do not fit at all. **The deciding variable is context
length per session, not the scenario label** — size an island by
`KV tokens ÷ expected session context`, and keep a margin: the degradation is gradual and
begins well before the cache is full.

**If you deploy the split**, raise `max-num-seqs` per island only together with KV
headroom, and re-check `vllm:kv_cache_usage_perc` under your own traffic — the 16-session
coding rung above shows what running close to the limit costs.

**How to read the comparison.** Both options use the same 16 cards, so the fair question
is not "which service is faster" but *"for a given number of concurrent sessions, is it
better to run one 16-card service or two independent 8-card islands?"* Two islands split
the load, so an island carries half the total sessions — island rung *N* is therefore
compared against 16-card rung *2N*. The decision rule applied below:

1. **Does the scenario fit on 8 cards at all?** The 8-card deployment is KV-bound to a
   65536-token window; a scenario whose sessions exceed that is 16-card only, regardless
   of latency.
2. **At matched total sessions, which side has lower ITL?** ITL drives how fast tokens
   stream back to a user and is comparable across the two topologies. (TTFT is not — the
   two run different prefill chunk sizes.)
3. **What does each option cost operationally?** Two islands halve the blast radius of a
   node failure and can be tuned per scenario, but each island admits at most
   `max-num-seqs` sequences, so a burst on one island queues instead of borrowing
   capacity from the other. One 16-card service pools all capacity but fails as a unit.

## Caveats

- **Numbers are steady-state, not cold-start.** See [Benchmark method](#benchmark-method):
  each rung is reported over its second half, once replayed sessions have reached
  realistic depth and the prefix cache is warm. A freshly started engine serves its first
  ~600 long-context requests several times slower; size for steady state, but expect the
  first minutes after a rollout to be worse.
- **TTFT is not comparable across the two topologies.** The 8-card deployment runs
  `max-num-batched-tokens` 4096 against the 16-card's 8192, so prefill is chunked
  differently. ITL, throughput and session capacity are comparable; TTFT is not.
- **The 8-card topology cannot serve the RAG scenario.** Measured RAG input lengths are
  mean 52k / p90 101k / max 125k tokens, so **30.5 % of RAG requests exceed the 8-card's
  65536-token window** — they cannot be served at all, not merely served slowly. Its
  375,260-token KV cache would also hold only ~7 full RAG contexts. The 16-card window
  (180224) fits 100 % of the corpus. **RAG requires the 16-card topology.**
- **Sessions, not requests.** The x-axis is concurrent agent *sessions*; one session has
  at most one request in flight, and replayed sessions idle between turns exactly as
  recorded. The idle fraction is workload-specific — chat and coding pause a median 0.3 s
  between turns, RAG a median 5.3 s — so N RAG sessions occupy only ~0.53 N request slots
  while N chat sessions occupy ~0.9 N. Request-per-second figures are correspondingly far
  below what a single-turn benchmark would show at the same nominal concurrency.
- **Single run per rung.** `numRuns: 1`, so the tables carry no run-to-run spread. ITL is
  a per-token statistic over thousands of intervals and is stable; **TTFT varies most**
  between repeats and should be read as an operating range, not a precise value.
- **Prefix caching is on and the corpus is multi-turn.** The engine reported an **84–89 %
  prefix-cache hit rate**, so only ~11 % of the ~22k input tokens per request are actually
  computed. A workload of independent one-shot prompts will show markedly higher TTFT and
  much lower session capacity at the same nominal input length.
